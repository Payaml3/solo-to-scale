## Ground rules

- **This prompt wins.** Where a file in `sources/` disagrees with this prompt, follow this prompt. The sources were written over time, and some details changed.
- **Use these terms everywhere:**
  - **phase:** A to G
  - **stage:** 1 to 30, the journey in the playbook
  - **slice:** a shippable increment with an exit check, inside stages 13 to 17
  - **story group:** 3 to 6 related stories built in one session

  A full handoff happens when a **slice** is done or the context guard fires. Never write "stage done" for build work.

- **Plan mode first.** Show me the file tree and the plan, and wait for my approval.
- **One source per thing.** Generated files carry a header: "Generated by solo-to-scale; edit `<source>`". CI fails if a generated file drifts from its source.
- **Scripts:** Python 3 standard library only, using `pathlib`. Every script has tests and must run on Linux, macOS and Windows.
- **No bundling of third-party plugins or skills.** Founder, Superpowers, marketing, brand-skills and Spec Kit are listed as recommended installs that `init` checks for.
- **No secrets anywhere.** Hooks never make network calls.
- **Every hook fails safe:** on any error it exits 0 silently, and it never blocks a prompt.
- Ask (AskUserQuestion) for anything marked **ASK**.
- **No project names in the plugin.** The plugin is generic. It never contains a startup's name, repo, epics, slices, invariants, view links or domain terms, and examples and fixtures use the fictional "Example Startup".
  - `init` asks the founder for the name and stores it once, in `founder/project.json`, with these fields:
    - `name`
    - `working_name` (true or false)
    - `repo`
    - `one_line`
    - `stage`
  - Templates use `{{project.name}}` and the other fields. Skills, hooks and session names (`<Project> · …`) read the file at run time.
  - **Renaming:** the founder edits `founder/project.json` and runs `upgrade`. `upgrade` re-renders the plugin-owned files, leaves founder-owned files alone, and lists where the old name still appears in them.
  - **CI:** `tests/check_no_project_names.py` fails the build if any file contains a name from the `PROJECT_NAME_DENYLIST` repository secret (comma-separated; skipped when unset). Keep it passing.

## 2b. The advisory board: four advisor roles

All four advisors advise and have no vote; the founder chairs and decides. All use the strongest model and read-only tools.

- **`growth-advisor`, the acquisition lens.**
  - It applies frameworks Alex Hormozi has published on offers and lead generation: offer value (dream outcome and likelihood of success against time delay and effort), four lead channels (warm outreach, cold outreach, content, paid ads), pricing on value, and lifetime value against acquisition cost.
  - It asks: does this make the offer more valuable; which channel brings the first 100 customers; what do we measure within 30 days.
- **`owner-advisor`, the long-term value lens.**
  - It applies principles Warren Buffett has set out in Berkshire Hathaway's shareholder letters: circle of competence, margin of safety, durable moat, capital allocation, avoiding ruinous or irreversible risk, reputation, patience.
  - It asks: is this within what we understand; what if we're wrong and can we survive it; does it widen the moat; is this the best use of the next pound or hour.
- **`customer-advisor`, the demand lens.**
  - It applies Paul Graham's essays on making something people want and doing things that don't scale, Rob Fitzpatrick's *The Mom Test* for honest interviews, and Marty Cagan's four product risks (value, usability, feasibility, viability).
  - It asks: who has this problem today and what do they do about it now; what did customers do, not say; what can we put in front of 5 real users this week.
  - It pushes back on building before evidence.
- **`risk-advisor`, the regulator's lens.** It's modelled on a role, not a person: a chief risk and compliance officer at a regulated business.
  - It covers the regulatory perimeter (where the product's activity would start to need a licence), anti-money-laundering where it applies, data protection, contracts, AI rules, and liability for agent actions.
  - It asks: would this make us regulated; what would a regulator, a client's compliance team or an auditor ask to see; what's the worst headline.
  - It's never legal advice, and says so. Its output always ends with whether a real lawyer is needed.
- **`board-review`, not `record-decision`, consults the advisors.** It runs when a significant decision is proposed, before the founder decides.
  - Advisors read only a one-page decision brief, never the repo.
  - It asks only the advisors the routing table names. Keep the table in `founder/team.md`:

  | Decision | Advisors |
  |---|---|
  | Pricing, positioning | growth, owner, customer |
  | Scope, a new feature | customer, risk |
  | Fundraising, large spend | owner, growth |
  | Go-live, data, partners | risk, customer |
  | Hiring | owner |
  | Anything else hard to reverse | owner, risk |

- **Later:** a template for a `sales-advisor` role (founder-led enterprise selling, deal qualification, buying committees). It's off by default, and `init` asks whether to enable it at stage 20.
  - Each advisor writes at most 8 lines: verdict (support, concerns or oppose), biggest risk, what would change its mind, one metric to watch.
  - Claude summarises where they agree and disagree.
  - The memos go in `founder/board/<decision ID>.md`, linked from the decision row.
- **The quarterly review** asks all four advisors to check the strategy against the evidence.
- **The team view** shows the board beside the founder: four advisor seats, each with its lens.
- **Rules, written into every advisor role file:**
  - name the advisor by its lens, never as the real person
  - never write as if the person said it, never invent quotes, never claim endorsement
  - paraphrase frameworks rather than copying text from the books or letters
  - no advisor names in anything public
- **Test:** an advisor's output on a sample decision contains no quotation marks attributed to a real person, and no first-person claims to be that person.

## 3. `init`: set up a startup's repo

It works like Phase 0 and Phase 1 of the bootstrap prompt.

**Assess first, read-only.** Report:
- what exists in the repo
- whether the default branch is current
- duplicates
- which recommended plugins this session can see

Then list the **ASK** questions together:
- the project's name, and whether it's a working name, plus its repo, one line and stage. Save them to `founder/project.json`; every file that needs the name reads it from there. If the product's code has its own brand setting, point it at the same name and say so in the PR
- the four context-guard limits
- the monthly budget for each role
- whether to enable recommended plugins in the repo settings
- whether interfaces use React

**Then scaffold from `templates/` onto branch `ops/solo-to-scale` and open one PR.** It never overwrites a file. Where a file exists, it proposes a merge in the PR description instead.

- `AGENTS.md` is the single instruction file. `CLAUDE.md` imports it and adds only Claude-specific lines. The two together stay under 200 lines, because an imported file loads too; the governance check counts them together.
- `founder/`:
  - project.json: name, working name or not, repo, one line, stage
  - operating-protocol.md
  - status.md
  - decisions.md
  - business-context.md
  - brand.md
  - playbook.md: 30 stages, gates including the engineering standards
  - team.md
  - artifacts.md
  - `sources/`
  - `claude-project/`: instructions, the knowledge list and scheduled-task prompts. The knowledge list is exactly these 8 files: `operating-protocol.md`, `AGENTS.md`, `HANDOFF.md`, `status.md`, `team.md`, both decision registers, and `business-context.md`. Everything else, the playbook included, is read on demand.
  - `.solo-to-scale-version`
- `docs/engineering-standards.md` and `HANDOFF.md`
- `.claude/settings.json`: plugin enabled, least-privilege permissions, hooks via the plugin
- `.codex/config.toml`: the same policies for Codex
- `.claude/governance.json`: limits, plus `claude_md_max_lines` and `pr_warn_lines`
- `tools/`:
  - `check_governance.py`
  - `build_roadmap.py`
  - `build_traceability.py` and `build_team.py`, generalised. Both read the epic-to-role mapping from `founder/team.md`, the only copy. In the dashboard, Architecture counts criteria in the architect's epics, Engineering counts the engineers' epics, and Founder HQ counts decisions resolved.
  - `claim.py`
  - `test-area` support
- `.github/`:
  - workflows: governance check, roadmap and view-data drift checks, and an optional cross-review job where Codex reviews Claude's PRs and the reverse, off by default (**ASK**)
  - `ISSUE_TEMPLATE/story-group.md` with the goal chain
- Labels: `role:*`, `claimed`, `blocked`, `founder-item`. Create them only after **ASK**.

**Views and cost rules:**
- **One progress view and one team view.** The progress view is a Data dashboard built from the traceability and roadmap data. Any older roadmap page is retired, after **ASK**.
- **`publish-views` is the only thing that publishes,** on the Monday scheduled task.
- **Role budgets are advisory.** The weekly review warns at 80% and proposes a pause at 100%; it never claims to enforce one.
- **The weekly review runs on the mid-tier model.** The quiet-week stop keeps it cheap; the smallest model is for formatting and renames only.
- **In the repo settings, enable only the plugins the project needs,** and recommend disabling unrelated ones (social media, for example). Their skill descriptions load into every session.

**End with the manual steps:**
1. Create the Claude Project from `founder/claude-project/`.
2. Create the Monday scheduled task.
3. Add the plugin's marketplace on claude.ai.
4. Add the repo secrets.
5. Before stage 6, where `product-design` is first used, confirm the design skills are available. At stage 11, run `design-system` to set the foundations.
