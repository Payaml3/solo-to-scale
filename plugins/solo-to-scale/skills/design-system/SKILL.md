# design-system

**Read narrowly.** Never read a whole file over 150 lines. Use `grep -n`, then read only the line ranges you need. Use `git diff` and `git log` to see changes.

Model: strongest for foundations and framework decisions; mid-tier for individual components and reviews. New content starts as Proposed; only the founder approves.

## 1. Assess first (read-only, at most 40 lines)

Per interface (app, admin, dashboard, marketing site): stack, styling, existing tokens and **where they're duplicated**, components, gaps. List design decisions already made, with their register IDs. Recommend the skills to use (brand-skills, `design-taste-frontend`, `impeccable`, `frontend-design`, an accessibility tool), the token roles, type and spacing scales, the first components, and the decisions still missing, each with options and a recommendation. **Implement nothing until the founder approves.** Then build on `design/system-foundations` and open one PR.

## 2. Stack rule

shadcn/ui and Tailwind only where the interface already uses React (the React answer from `init`). Otherwise keep the current stack and build the same components natively (Jinja macros, Astro components or the framework in use) with the same tokens, variants and states. Adding React or Tailwind is a framework change: propose it as a decision, never make it.

## 3. Tokens have one source

`design/tokens.json` (or an existing equivalent the assessment finds). Semantic roles (`surface`, `text-muted`, `status-blocked`), never raw colours; the brand palette maps onto the roles. A small script generates each interface's CSS variables or theme from it; generated files carry the "Generated by" header and are never edited by hand. Details: `references/tokens.md`.

## 4. Who leads when

- **Design system and the public website:** taste (`design-taste-frontend`) leads. It proposes 2 or 3 directions from `founder/brand.md`; the founder picks one; it becomes `tokens.json`, recorded with `record-decision` Each direction may start from a company's DESIGN.md in [awesome-design-md](https://github.com/VoltAgent/awesome-design-md) (MIT), picked for products that look like this one. The chosen one is adapted into `DESIGN.md` at the repo root (look, rules, do's and don'ts; values point to `tokens.json`), never a copy of another brand's name or marks.
- **Product screens:** `design-system` and `product-design` lead. Taste only reviews, within the existing tokens and components, and may not add colours, fonts or components without a decision.
- **Design QA:** one reviewer per pass: taste for visual quality, `impeccable` for UX and accessibility. Never both on the same pass.

## 5. Components evolve safely

Additive variants; deprecate before removing; no duplicate components; no arbitrary values.

## 6. Docs and checks

- `docs/design-system/`: `README.md`, `tokens.md`, `components.md`, `patterns.md`, one page each, only what the code doesn't say. Prefer a living component page.
- Add to `tools/check_governance.py` (or the frontend lint): fail on raw colour or spacing values outside the token source and generated files; fail if a generated token file doesn't match `tokens.json`; run the accessibility check in CI on the component page and key screens. See `references/checks.md`.

Don't install memory plugins: the repo is the memory. Close with `handoff`.
